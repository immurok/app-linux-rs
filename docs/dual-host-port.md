# 双主机支持：Linux 侧移植说明

固件与 macOS app 已实现并实机验证（固件 1.6.14，2026-08-04）。Linux 侧
**尚未开始**。这份文档是给在 Linux 机器上接手的人/agent 的完整交接 ——
`app-linux-rs` 作为独立仓库时不含固件源码，也不含 monorepo 里那份设计
spec，光看 Rust 代码是推不出下面这些语义的。

monorepo 里的完整设计：`docs/superpowers/specs/2026-08-03-dual-host-design.md`。

---

## 1. 用户视角

一台设备最多绑 **2 台主机**。任一时刻只对其中一台可见。

- **切换主机**：按设备上的**切换指纹**（指纹槽索引 5，专用，不参与认证）。
  设备写标记页后软复位，换一个 BLE 地址重新广播。槽 1 蓝灯闪、槽 2 白灯闪。
- **绑定第二台**：在那台电脑上点配对 → 按一次**已登记的认证指纹** → 按一下
  **设备按钮**。老主机全程不参与，不需要开机、不需要输任何码。
- **解绑**：本机解绑自己的槽；也可以解绑另一台（那台丢了/不在身边），后者
  要按一次已登记指纹。

早期设计用过「老主机签发 6 位临时 PIN，新主机输入」的方案，已完整实现后
移除——设备就在用户手里，人、设备、新主机同处一室，带外 PIN 挡的中间人
在这个场景下不存在。**看到任何提到 PIN 签发、`0x3A`、`0x3B`、`K_pin`、
`proof` 的旧文档或旧分支，那都是已删的。**

## 2. 协议增量（相对固件 1.6.12 之前）

### 2.1 新命令

**`CMD_SLOT_STATUS = 0x39`**，无 payload。未配对也可读 —— 新主机正是靠它
得知自己是第几台。

```
应答: [0x39][0x00 OK][bitmap][active]        4 字节
      bitmap: bit0 = 槽 1 已占, bit1 = 槽 2 已占
      active: 1 或 2，当前活动槽
```

旧固件回 `[0x39][0xFE]` 之类，据此判定「设备不支持双主机」，不要当错误。

**`CMD_SLOT_CLEAR = 0x3C`**，payload 可选 `[slot]`（1 或 2），缺省 = 本机
所在的槽。**两条路径的协议完全不同**：

| | 清自己的槽（payload 空，或 slot == active） | 清另一个槽（slot != active） |
|---|---|---|
| 指纹门 | **无** | **有** |
| 应答 | `[0x3C][status]` 2 字节 | 先 `[0x11]` 1 字节，指纹过后再 `[status]` 1 字节 |
| 之后 | 设备**重启** | 不重启，连接不断 |

清自己的槽不要指纹，是因为命令本身已经走在这条槽的加密链路上，再要一次
生物特征拦不住任何人。

### 2.2 新通知

**`[0x34][0x03]`** = 「登记第二台主机时，指纹这一重已通过，转入等按键」。
纯进度信号。已有的 `0x34` 状态：`0x00` 超时、`0x01` 按键已按下、`0x02`
长按取消。收到未知状态码要忽略（向后兼容）。

没有这条通知就无法诚实地驱动两步引导 UI —— 只能猜第一步何时完成，而猜出来
的「已完成」会在用户还没按指纹时就点亮。

### 2.3 语义变更（无新命令，但行为变了）

**`GET_STATUS` 的 paired 位（应答第 3 字节）现在报的是「活动槽是否已配对」，
不再是「任一槽已配对」。** 这是「跟你说话的这台主机配对了没有」，正是主机
侧该关心的那一位。

踩过的坑：曾经报「任一槽」，于是主机 2 走空的槽 2 连上来也被告知"已配对"，
app 按已配对视角渲染，却拿不出共享密钥做验证，红字报验证失败，而真正该出现
的配对入口反倒不显示。

**BLE bond 模式按活动槽决定**：活动槽已配对 → `NO_PAIRING`（拒绝新 bond，
防盗贼另配）；活动槽是空的 → `WAIT_FOR_REQ`。要让设备停在空槽本身就得按
切换指纹，那已经是一道生物特征门。

### 2.4 指纹槽

固件 `FP_USER_MAX` 从 5 增到 **6**。索引 **5** 是专用的**切换指纹**，
只切槽、绝不参与认证。可用于认证的仍是索引 0–4。

`protocol.rs` 的 `MAX_FINGERPRINT_SLOTS = 5` 语义不变（认证槽数），但
UI 需要能登记/显示第 6 个槽，且必须标明它的用途不同。

## 3. 三个必须知道的约定

1. **指纹门的结果一律是 1 字节纯状态**，不带命令码。写成 `[cmd][status]`
   会被读成命令码从而永远判失败 —— macOS 侧在 SLOT_CLEAR 上刚踩过。

2. **`PAIR_INIT` 对第二台主机也回 `[0x30][0xF0]`(WAIT_BUTTON)**，与首次
   配对一样。区别只在设备内部多挂了一道指纹门。主机侧的状态机因此不用分叉，
   照旧等 `[0x30][pubkey:33]` 通知即可。要区分提示文案（"按按钮" vs
   "先按指纹再按按钮"）就先查 `SLOT_STATUS`。

3. **查槽位要在发 `PAIR_INIT` 之前完成**。并发发起的话 `WAIT_BUTTON` 可能
   比槽位应答先到，提示就用错分支渲染出去了。

## 4. Linux 侧待做清单

### 4.1 危险项，优先处理

**`PAIR:RESET` 目前会给设备发 `CMD_FACTORY_RESET`**（`socket.rs`
`handle_pair_reset`），而 CLI 的 `imk unpair` 走的就是它。在双主机下这意味着
**一台 Linux 主机执行 unpair 会连带毁掉另一台主机的槽和设备上全部 SSH 私钥**。

必须改成：`unpair` = `SLOT_CLEAR` 自己的槽 + 清本地配对数据。factory reset
留作独立的、有明确警告的命令。

（macOS 侧的对偶 bug 是反向的：unpair 只清本地、从不告诉设备，于是重新配对
被守卫要求 factory reset，用户卡在"解绑了却配不上"。两边都错，方向相反。）

#### 单主机 unpair 是一扇单向门（固件问题，留给固件侧）

活动槽未配对时，固件的命令白名单（`hidkbd.c:4908-4922`）只放行 6 条：
`GET_STATUS`、`GET_BATT_RAW`、`PAIR_INIT`、`PAIR_CONFIRM`、`PAIR_STATUS`、
`SLOT_STATUS`。**`CMD_FACTORY_RESET` 和 `CMD_DELETE_FP` 都不在里面**，都回
`SEC_ERR_NOT_PAIRED`。而 `PAIR_INIT` 在两个槽都空且仍有指纹时回
`SEC_ERR_NEEDS_RESET`（`hidkbd.c:5241`：`slot2_enroll = !active_slot_paired()
&& is_paired()`，两槽皆空时为假）。

于是：**只绑了一台主机、且已登记指纹的用户，一旦 unpair 成功，就配不上、
重置不了、也删不掉指纹**——只剩长按按钮 3 秒（`hidkbd.c:1746`），而它会连同
全部 SSH / OTP / API 私钥一起擦掉。双主机场景没这个问题（另一槽还占着，
`slot2_enroll` 为真，`PAIR_INIT` 放行）。

客户端只能绕，不能修：`unpair_own` 先用 `SLOT:STATUS` + `FP:LIST` 预检，命中
就改印真实后果并要求输入完整 `yes`，同时给出可行顺序——**先删指纹再 unpair**
（指纹清零后 `PAIR_INIT` 就放行了）。

**结构性修复在固件侧：把 `CMD_FACTORY_RESET` 加进那张未配对白名单**（它本来
就有自己的指纹门，没有指纹时直接执行，不依赖配对密钥——daemon 侧
`handle_factory_reset` 已经记着固件既不读 payload 也不校验 HMAC）。接手固件
的人请从这里开始。

### 4.2 功能

- `protocol.rs`：`CMD_SLOT_STATUS`/`CMD_SLOT_CLEAR`、`PAIR_BUTTON_FP_OK`、
  `SWITCH_FINGER_SLOT`、`SLOT_1`/`SLOT_2`
- `socket_proto.rs`：`SLOT:STATUS`、`SLOT:CLEAR[:<n>]`
- `ble.rs`：`0x34/0x03` 通知的处理（进度）；`SLOT_CLEAR` 两条路径分别走
  `ble_send` 与 `ble_send_fp_gated`
- `socket.rs`：两个 handler。注意清自己的槽时设备会重启，应答可能随链路一起
  丢掉——那种情况下设备其实已经清干净了，本地要照清，否则用户卡在"清不掉"
- CLI：`imk slot status` / `imk slot clear [n]`；`imk pair` 打印两步引导
- TUI：两张主机卡片（本机标记 / 绑定状态 / 各自的操作）

### 4.3 已知不适用的部分

macOS 侧有一处「app 在本地镜像固件的拒绝规则（有指纹就拒绝配对）」，
固件给这条规则加了第二台主机的例外后镜像没跟上，导致 `PAIR_INIT` 根本发不
出去。**Rust 侧没有这个镜像预检**，天然不受影响，不要照搬着加。

## 5. 验证状态

已实机验证（2026-08-04，macOS + 固件 1.6.13）：

- 第二台主机绑定全流程（指纹 + 按键）
- 槽间切换、每槽独立 BLE 地址、两条 bond 并存（需 `-DBLE_SNV_NUM=2`，
  WCH 默认 1，否则第二台 bond 会顶掉第一台的 LTK）

未验证：

- 跨槽解绑（`SLOT_CLEAR` 带目标槽 + 指纹门）——只做过编译和静态检查
- Linux 侧全部
